# Задание 2. Разделение системы на домены и потоки данных

## Выделенные домены

1. Домены клиник (Healthcare)  
Хранение и обработка операционных данных клиник: расписания, операции, ресурсы, агрегаты без PHI в витрине  

2. Домены ИИ и медицинских изображений (AI и Imaging)  
Хранение и обработка медицинских изображений, извлечение признаков, подготовка данных для обучения и инференса моделей  

3. Финтех-домены (Fintech)  
Финансовые транзакции, счета, кредиты, риск-скоринг, отчетность для банка  

4. Фармацевтические домены (Pharma)  
Каталоги препаратов, производственные и дистрибьюторские данные, поставки, запасы  

5. Домены медицинского оборудования (Med-Devices)  
Телеметрия оборудования, события, данные эксплуатации и логистики  

6. Легаси-домен (Legacy)  
Исторический DWH на SQL Server и старые интерфейсы, которые остаются на переходный период  

## Принципы разделения

#### Принцип 1. Разделение контекстов бизнеса  

Используется подход DDD. Каждый домен соответствует своей предметной области, а команды, работающие с данными, управляют ими в границах своего контекста  

#### Принцип 2. Единая инфраструктурная платформа  

Общая технологическая основа для потоков данных, хранения и аналитики. Она обеспечивает интеграции, управление доступом, поиск и обнаружение данных  

#### Принцип 3. Продуктовое мышление  

Данные рассматриваются как продукт.  
Для «покупателя» данных важны:  
- Доступность для поиска : насколько легко найти нужный продукт данных  
- Доступность по адресу : скорость и простота получения доступа к данным  
- Достоверность : уверенность в качестве и надежности данных  
- Документирование : описание и lineage в каталоге данных  
- Взаимодействие и стандарты : соответствие корпоративным политикам и отсутствие дублирования  
- Безопасность и управление доступом : политики RBAC/ABAC для безопасного использования  

#### Принцип 4. Управление через единые политики  
Существует отдельная группа экспертов, которая определяет стандарты и политики качества данных. Они автоматизируются на уровне платформы. Каждая команда домена отвечает за свои продукты данных и публикует контракты для использования другими доменами  

## Подход Data Mesh

Подход Data Mesh рассматривает данные как продукт. Владение данными и управление ими передается экспертам в предметной области.  
Ключевые компоненты Data Mesh:  
1. Данные как продукт  
2. Владение данными на уровне домена  
3. Самообслуживающаяся платформа для данных  
4. Глобальные политики и стандарты  

При переходе к Data Mesh бизнес получает:  
- Гибкость за счет независимого развития доменов  
- Улучшение качества и скорости работы с данными  
- Соответствие требованиям комплаенса  
Возможность быстрого масштабирования  

## Data Flow Diagram (DFD)

Потоки данных между доменами можно описать так:  

1. Источники данных (клиники, банк, фармацевтические компании, устройства) публикуют события и данные через слой интеграции  
2. Данные обрабатываются и попадают в Lakehouse, где разделяются по доменам  
3. Каждый домен формирует собственные Data Products и публикует их через каталог данных  
4. BI-портал и витрина данных используют продукты разных доменов для формирования отчетов и дашбордов  
5. Домены могут обмениваться продуктами данных напрямую через контракты, обеспечивая повторное использование  

## Преимущества разделения на домены

1. Независимое развитие бизнес-направлений без необходимости изменять общий DWH  
2. Сокращение времени интеграции новых бизнесов и компаний  
3. Увеличение прозрачности и доверия к данным через каталог и политику качества  
4. Повышение гибкости и скорости создания аналитики и отчетности  
5. Соответствие требованиям безопасности и регуляторики за счет четкого разграничения доменов и политик доступа
